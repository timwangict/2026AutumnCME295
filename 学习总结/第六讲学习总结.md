## 一句话主旨

**LLM 只能「回答」，Agent 能「动手」。** 本讲回答一个问题：怎么把只会「预测下一个 token」的 LLM，改造成一个能查资料、调工具、做多步任务、甚至操作电脑的「智能体」？答案是一条不断补能力的链：**检索（RAG）补「知识」，工具调用（Tool calling）补「行动」，Harness 补「多步循环与记忆」，最后落到 Coding agents。**

---

## 开场：为什么需要 Agent（两大局限）

Afshine 用「写代码」讲了一条演进线：

```
2022 ChatGPT 问世（帮写代码，靠 prompt 一问一答）
→ 2024 IDE 自动补全（tab tab tab，靠 next-token 预测）
→ 2025 能完成整个任务（帮你写、测、部署）
→ 2026 出现 agentic 行为（自主端到端）
```

而 LLM 之所以不能一步到位，有两个**核心局限**：

1. **知识被训练数据锁死**：模型只知道训练截止日前的东西（如 GPT-6 Astra 的 knowledge cutoff 是 2026-04-30）。它没见过的（你的私有代码库、刚发生的中期选举结果）一概不知。
2. **只能回答、不能行动**：你让它「帮我下单一个 17 英寸泰迪熊」，它只会回一句话，因为它只会生成文本、不会执行动作。

## 模块一：RAG 检索增强生成（补「知识」）

### 为什么不能把所有信息都塞进 prompt？

三个约束层层递进：
1. **上下文有限**：1M token 也装不下「训练截止后发生的所有事」。
2. **输入越大越差**：**Needle in a Haystack（大海捞针）测试**证明——输入越长，模型越难捞出藏在开头的信息，性能退化。
3. **成本**：按 input token 计费，塞得越多越贵。

所以答案是：**只塞「和当前任务相关的」信息** —— 这就是 RAG。

### RAG 三步

```
Retrieve（检索相关文档）→ Augment（把文档塞进 prompt）→ Generate（生成回答）
```

### 知识库怎么建

收集文档 → **分块（chunk）** → 每块用 encoder 编码成 **embedding 向量**。三个超参数：
- **embedding size**：内容越微妙越要长，通常**数千维**；
- **chunk size**：不能太大（输入不能太大），通常**数百 token**；
- **overlap**：块间重叠，通常 **~10%**（避免把一句话从中间切断、丢上下文）。

### 检索是「两步走」

| 步骤 | 目标 | 方法 | 特点 |
|------|------|------|------|
| ① 候选检索 Candidate retrieval | 最大化 **recall**（宁多勿漏） | **bi-encoder** + 近似最近邻（ANN） | 便宜，能扫百万级文档，取 ~100 候选 |
| ② 重排序 Reranking | 精细化排序 | **cross-encoder**（query+chunk 一起过单个 BERT 式 encoder，CLS 投影出相关性分数） | 贵，只对 100 个候选做，能捕捉 token 级细粒度关系 |

**bi-encoder vs cross-encoder 的关键区别**（本讲最硬的点之一）：
- bi-encoder：query 和 chunk **分别**编码成两个向量再算相似度 → 快（chunk 向量可预计算），但丢失了 query 与 document 之间 token 的交互细节；
- cross-encoder：query 和 chunk **拼成一条序列**过同一个模型 → 慢（每次都要现算），但能建模「query 里的词 vs 文档里的词」的交互，更精确。

所以经典套路是「**先用便宜的 bi-encoder 海选，再用贵的 cross-encoder 精选**」。

### 语义相似 vs 关键词匹配：要混合

- **语义相似**（embedding 余弦）：能理解同义改写，但可能把「Cuddly（泰迪熊）」和「Huggy」混在一起，或把「where is Paris located?」当成同类问题——会误召回。
- **关键词匹配（BM25）**：精确匹配词，但「换个说法」就漏。
- **正解：hybrid 混合**（把两种排名融合），多数情况优于任一单独用。

### 检索的两个进阶技巧

- **HyDE（Hypothetical Document Embeddings）**：先让 LLM 从 query「脑补」一篇假文档，再用假文档去和 chunk 比相似度——因为「文档 vs 文档」比「问题 vs 文档」更容易对齐。
- **多查询重写**：一个 query 里可能含多个问题，拆成多个子问题分别检索。

### 分块丢上下文 → Contextual Retrieval

块切得再小心，单块仍可能看不懂。解法：**让 LLM 基于整篇文档给每块补一句上下文**，使每块自包含。省钱的 trick：把「整篇文档」放 prompt 固定位置，这样能吃到 **prompt caching** 的折扣（cached input 便宜约 10 倍）。

### 检索怎么评测

| 指标 | 含义 |
|------|------|
| **NDCG@k** | 归一化折损累计增益：排名越靠前的相关文档得分越高，用「完美排序」归一化到 0~1 |
| **Reciprocal Rank** | 1 ÷ 第一个相关文档的排名 |
| **Recall@k** | 所有相关文档里，top-k 抓到了几个 |
| **Precision@k** | top-k 里，真正相关的占多少 |

> 关键点：**候选检索阶段盯 recall，重排阶段盯 precision**。

### 代码场景：RAG 失效，改用 grep

代码问题你要的是**精确匹配**（某个函数名出现在哪），语义相似反而不对。所以 coding agent 里用 **grep**（精确正则搜索），而不用传统 RAG。

## 模块二：Tool calling 工具调用（补「行动」）

### 为什么需要工具

RAG 只能查**静态数据库**，但「帮我找找附近的泰迪熊」需要**实时交互**（查 GPS、查后端）+ **执行动作**。这就是工具（tools）。

### 工具调用三步流程（本讲核心）

```
① LLM 预测要执行什么（生成 tool call + 参数）   ← LLM 干的
② 执行动作（backend 真正运行，与 LLM 无关）      ← 环境干的
③ 结果喂回 LLM，生成最终回答                    ← LLM 干的
```

> 关键认知：**LLM 只负责「决定用什么工具、传什么参数」和「把结果转成人话」，真正执行动作的是 backend。**

### 工具怎么写

用 Python 函数 + **文档字符串（docstring）** 表达。重点：
- 给 LLM 看的只有 **API 描述 + 输入输出 schema**，代码逻辑是「实现细节」不给 LLM 看；
- **输入要可解释**（参数名清楚、带类型，如 `location`）；
- **输出要结构化**（用 enum 等，方便喂回 LLM 转成自然语言）。

### 工具的类型（万能）

web 搜索、天气/股票快捷查询、代码库查询、**计算器**（算术用确定性 backend，比 next-token 猜数可靠）、**代码执行**（画图）、**动作**（代你发邮件）。

### 工具使用从「训练」到「提示」的演变

- 一两年前：用 **SFT 两阶段**把工具调用训进权重（阶段一：预测 tool call + 参数；阶段二：把 backend 结果转自然语言）。
- 现在：**靠 prompting**（docstring 里写清楚怎么用），工具使用越来越是「原生能力」，写得够清楚就不需要额外训。

### Tool selection（工具选择）：工具太多会打架

工具多了会有 **scope conflict（范围冲突）**：
- **良性冲突**：两个工具输出相同（get_doc vs get_drive 都返回文档），无所谓；
- **有害冲突**：改变了对 query 的解释（「find my teddy bear」可能被「找电脑里的图片文件」的工具抢走，而不是「物理上找泰迪熊」）。

**缓解办法**：不把整个工具库都给 LLM，而是**选一个子集**。依据：
- 对话历史（在聊「物理泰迪熊」就选找位置的工具）；
- memory（过去类似 query 怎么选的）；
- 用户画像（金融岗 → 金融工具；工程师 → 代码工具）；
- 用户手动激活/停用的偏好。

路由模型用一个**轻量 LLM**（低延迟），两步：选子集 → 放进 context window。

另一个不用太多工具的理由：**context rot**（上下文越长，工具调用能力越退化）。

### MCP：工具标准化

**MCP（Model Context Protocol，Anthropic 2024）** = 让「一个工具」能接「所有支持它的 LLM」，不用为每家重写。两个角色：
- **MCP server**：装工具实现 + 业务逻辑；
- **MCP client**：调用 server 的客户端（用户只接触 client）。

MCP 把能力分成三个 bucket：**tools**（工具）、**prompts**（工作流快捷方式）、**resources**（资源/数据）。

### Prompt caching：工具描述不贵

工具描述、指令这些「固定内容」会反复出现，用 **prompt caching** 省成本（cached input 便宜约 10 倍）。

**一个练习（本讲的小考点）**：prompt 的消息顺序要**把固定部分放最前面**，才能命中缓存。顺序是「user prompt + tool definitions + user context」，如果固定部分（工具定义）不在顶部，就吃不到缓存。缓存还有 **TTL（time to leave）**：5 分钟 / 1 小时等，高频复用的场景选短 TTL 划算。

## 模块三：Harness engineering（补「多步循环与记忆」）

### Harness 是什么

**模型之外的一切**：tools、动作排序、compaction 策略、memory、prompting…… 类比：**模型 = 引擎，harness = 车其余部分**，两者互补，弱模型 + 强 harness 也不行，反之亦然。

### Harness 到底包含 tools 和 RAG 吗？

讲师原话（转写稿）把 harness 定义为「**除了模型之外、包围着模型的一切**」（everything surrounding it but the model），并明确点名了四样：

| 明确包含 | 说明 |
|---|---|
| ✅ **Tools** | 原话 "it **includes tools** that we covered"，工具明确算在内 |
| ✅ 动作排序 | how actions should be ordered |
| ✅ Compaction + Memory | 上下文压缩策略、记忆 |
| ✅ Prompting | 和提示词相关的一切 |

那 **RAG** 呢？讲师下定义时**没有点名 RAG**，要分两层看：

1. **按「模型之外的一切」这个总定义**：RAG 的检索器、知识库、embedding 都在模型之外，宽泛意义上算 harness 的一部分。
2. **按实践落地**：RAG 的「检索」这一步，在绝大多数 agent 框架里就是以一个 **tool（search / retriever）** 的形式存在，所以它往往**通过 tools 这条线被 harness 间接覆盖**。

但要注意：**课程的教学结构里，RAG / Tool calling / Harness 是三个并列的模块**（分别补「知识」/「行动」/「循环与记忆」），而不是「harness 包含 RAG」的从属关系。

> 一句话：**Tools 是 harness 明确列举的组成；RAG 讲师没点名，但按「模型之外的一切」的定义属于 harness，且通常以 tool 的形式被 harness 承载。**

### ReAct：Reason + Act（2023 范式）

Agent 的核心循环：

```
Observe（观察当前状态）→ Plan（规划动作）→ Act（执行）→ Observe → … 直到满意才输出
```

例子（恒温器 agent）：泰迪熊冷 → 观察到「温度相关」→ Plan「先测温度」→ Act「调测温工具」→ 观察到「温度偏低」→ Plan「升温」→ Act「调升温工具」→ 验证温度 OK → 输出。

> 观察/规划/执行这三步，主要是 **SFT 训出来的原生能力**；每次执行工具后都有一段「复盘」——这是「必要的推理」，但不等于推理模型的「额外推理层」。

### Agent 间通信：A2A

类似工具有 MCP，agent 间有 **A2A 协议**（2025 发布），让不同 agent 说同一种语言、互相调用技能。

### Context compaction（上下文压缩）

上下文总会塞满，三种策略（可组合）：
1. **删除**：删掉只在下一次 turn 有用的 tool output；
2. **时间/滑动窗口**：只保留最近 N 轮；
3. **摘要**（最流行）：把历史总结进**预定义 buckets**（如 Pi coding agent 的「current progress / remaining work」），用简短摘要继续对话。

### Memory（记忆）

- **短期记忆** = context window（花哨词，就是上下文）；
- **长期记忆**：两种做法——对过去对话做 RAG 检索，或用一个 **memory tool** 把「要记住的东西」存起来。

> 压缩后，**reasoning trace（思考链）不会原样保留**，只留「用户想干嘛」的高层 gist。

## 模块四：Coding agents（集大成）

核心就是 **ReAct + 工具循环 + 执行环境**。几个独有特点：

1. **auto-approval（自动审批）**：过去每个动作都要人点 allow/deny，现在用一个**轻量模型独立判断动作安全性**，自动放行。
2. **用 grep 而非 RAG**：regex 精确匹配比语义检索更准、更快，喂给推理阶段效率极高。
3. **AGENTS.md**：标准化规则文件，把「每个 session 都要让 agent 知道的偏好」持久化，用户可控。
4. **Skills（技能）**：把重复工作流写成「recipe」（prompting + 脚本 + 相关文件），下次直接调用。高效做法：**先端到端做一遍，再让 agent 把它重构成一个 skill**。

### 生态

- **Pi**：minimalist harness（提示词最少），能看清模型「最原始」的表现，常用来做跨模型 benchmark 对比。
- **Computer use**：靠截图 + 预测下一步操作电脑，目前低效（要等两讲后才有新希望）。

### 多 agent

- **subagents**：把「不需要太多推理」的任务委派出去，有成本（每次要建独立 context）；
- **agent swarms**：多个 agent 协作，有通信渠道分享进度——能做出数学突破，也有风险（如 Hugging Face hack）。

## 关键数字 / 术语速记

| 术语 | 一句话 |
|------|--------|
| RAG | Retrieve-Augment-Generate，只塞相关信息进 prompt |
| chunk | 文档切的小块，数百 token，块间 ~10% overlap |
| bi-encoder | query/chunk 分别编码，快（可预计算）但丢交互 |

| MCP | Model Context Protocol，工具标准化（server/client，tools/prompts/resources） |

| ReAct | Reason+Act：Observe→Plan→Act 循环 |

## 一句话收尾

> **Agent = LLM（引擎） + Harness（车体）**：RAG 让引擎「看得见当下」，工具让引擎「动得了手」，ReAct + 记忆让引擎「能多步思考」，coding agent 则是把所有能力装进一个会操作你电脑的循环里。这一讲是「模型能力」到「实际干活」的桥梁。
