## 一句话总结

**前四讲讲"模型长什么样、怎么训"，这一讲讲"怎么让这么大的模型，真能在硬件上跑起来"**——整讲被两个问题贯穿：**① 怎么让模型"装得下"（fit）？② 怎么让它"跑得快"（fast）？**

---

## 开场：为什么需要这一讲（动机）

LLM = 把 Transformer 的 **decoder 放大**，参数量动辄百亿~万亿，预训练要喂数万亿 token。而 decoder 内部其实只有两层：**掩码多头注意力 + 前馈网络**——这两层**本质都是矩阵乘法**。什么硬件最擅长矩阵乘法？**GPU**（有海量核心，可以并行算，矩阵的每个元素都能独立算）。

但 GPU 有两大硬限制：

| 限制 | 具体 |
|---|---|
| **内存有限** | 单卡 HBM 只有 100GB 量级；而 100B 参数模型按 FP16（每参数 2 字节）光存参数就要 200GB，装不下 |
| **算力/时间贵** | 训练要喂海量 token，推理要服务海量请求，都烧钱 |

于是全讲围绕「装得下 + 跑得快」展开。

## 第一部分：GPU 内优化 —— Flash Attention（Afshine 讲）

### 1. 先认识 GPU 的两块内存（关键前提）

| 内存 | 大小 | 速度 | 作用 |
|---|---|---|---|
| **HBM**（高带宽内存，片外） | ~100GB（大） | ~1TB/s（相对慢） | 存大中间结果、参数 |
| **SRAM**（片上） | ~100MB（小） | ~10TB/s（快一个量级） | 计算时临时用 |

**问题根源**：自注意力的 `Q·Kᵀ` 会生成一个 `n×n` 的方阵（n 是序列长度）。n=1000 时就是 100 万个数，n 上万时更大——这个大矩阵**传统上要写进"又大又慢"的 HBM**，反复读写，慢。

### 2. Flash Attention 的核心思想：别把 n×n 矩阵写进 HBM

softmax 的定义（第 1 讲学过）：

```
softmax(s)ᵢ = e^(sᵢ) / Σⱼ e^(sⱼ)
```

它的"麻烦"在于：**要算 softmax 第 i 项，必须先算完一整行的 Σe^(sⱼ)（分母）**——传统做法就得先把整行算出来、写回 HBM、再读出来 softmax、再写回、再乘 V。四次大读写。

Flash Attention 的洞察：**`softmax(s)·V` 其实能写成"分子 / 分母"，而分子分母都能"迭代更新"**：

```
softmax(s)·V  =  [ Σᵢ e^(sᵢ)·vᵢ ]  /  [ Σⱼ e^(sⱼ) ]
                  └── 分子 n（可迭代累加）──┘    └── 分母 d（可迭代累加）──┘
```

这样就不用"先算完整行"，而是：**把一小块 K、V 搬进 SRAM → 更新分子分母 → 再搬下一块**，全程只在快内存里算，最后一步才除一次。**关键：全程不需要把 n×n 矩阵物化（materialize）到 HBM 里。**

### 3. 一个数值稳定的细节：为什么要"缩放"（rescaling）

问题：`e^x` 在 x 很大时会**爆炸**（数值溢出）。

解法：分子分母**同时乘以同一个常数** `e^(−m)`（m = 当前已见过的最大值），比值不变，但能把指数"压下来"：

```
乘 e^(−m) 后：e^(sᵢ) 变成 e^(sᵢ − m)，而 sᵢ − m ≤ 0，不会爆炸
```

新元素进来时，若最大值 m 更新了，就把**之前累加的总和也乘以 e^(m_old − m_new)** 重新对齐。这就是论文里那堆看着吓人的公式背后的两件事：**迭代累加 + 防溢出缩放**。

### 4. 三个关键结论（务必记住）

1. **Flash Attention 是"精确"方法，不是近似**——它和标准 softmax 算出的结果完全一样，只是"搬运数据的方式"更聪明。
2. **训练反向传播时，宁可"重算"也不"存储"**：反直觉——通常算过的东西不该再算，但这里"重算 n×n 矩阵"比"存到慢内存再读"更快。所以 Flash Attention 训练时 **GFLOPS 更高（75.2 vs 66.6），但总耗时反而更短**。
3. 后续 FlashAttention 2/3/4 是在此基础上针对新 GPU（Hopper 的 H100/H200、Blackwell 的 B100/B200）做的进一步优化。

## 第二部分：多 GPU 并行训练（Afshine 讲）

单卡装不下怎么办？用多卡。五种并行方式（俗称"5D 并行"，可混合用）：

| 并行方式 | 切的是什么 | 一句话 |
|---|---|---|
| **数据并行 Data Parallelism** | 数据（batch） | 每个设备放一份完整模型，各自吃一部分数据，最后同步梯度 |
| **张量并行 Tensor Parallelism** | 单个矩阵运算 | 多头注意力的各 head、FFN 的矩阵，拆到不同设备算 |
| **流水线并行 Pipeline Parallelism** | 模型的层 | 前几层放设备 A，后几层放设备 B，像流水线一样传 |
| **上下文并行 Context Parallelism** | 序列长度 | 长序列的 token 分组，各设备算自己的 query，再交换 K/V |
| **专家并行 Expert Parallelism** | MoE 的专家 | 每个专家放一个设备，token 路由到对应专家的设备 |

**重点记两个**：

- **ZeRO（Zero Redundancy Optimizer，数据并行的升级版）**：普通数据并行要在每张卡都复制参数、梯度、优化器状态（大量冗余）。ZeRO 把这三样**分片（shard）**到各卡——需要时通过通信向别的卡取。代价是**多了通信开销**，但换来了"每卡存更少"。它和模型并行的本质区别：ZeRO 里**整条前向传播还是在同一张卡上算**，只是"缺的参数临时向别人借"。
- **流水线并行的"气泡（bubble）"**：前一层算完传给下一层时，前面的卡会**空闲等待**，这段空闲叫 bubble。有各种调度策略来减少它，但讲里未展开。

> 一句话收束：并行不是免费的——你是在用"设备利用率下降 + 通信开销"换"内存装得下"。GPU 很贵（按小时租），所以不能无脑开到最大并行。

## 第三部分：推理优化（Shervin 讲）

### 1. 先建立直觉：10 词问 10k 字输出 vs 10k 字输入要 10 词

哪个快？**后者快**。原因（这是推理优化的总钥匙）：

- **prefill（预填充）**：把 prompt 的所有 token **一次性并行**喂进去算 K/V，快；
- **自回归解码（autoregressive decode）**：生成时**一个 token 一个 token 串行吐**，慢。

所以"输出很长"最贵，因为输出是串行生成的。这也解释了为什么**输出价格 ≈ 输入的 5 倍**。

### 2. 三个延迟指标（做 infra 的人天天盯）

| 指标 | 全称 | 含义 |
|---|---|---|
| **TTFT** | Time to First Token | 从发请求到吐出第一个词的时间 |
| **TPOT** | Time Per Output Token | 之后每个词的耗时 |
| **TTLT** | Time to Last Token | 到最后一个词的总时长 |

infra 主要优化 **TTFT 和 TPOT**（TTLT 受模型"思考多久"影响，不完全是系统问题）。

### 3. Roofline 模型：判断"卡在内存还是卡在算力"

三个概念：

- **计算吞吐（compute throughput）**：每秒能算多少次（TFLOPs），取决于数据类型（低精度算得快）；
- **内存带宽（memory bandwidth）**：每秒能从 HBM 搬到 SRAM 多少数据；
- **算术强度（arithmetic intensity）= 计算量 / 内存搬运量**。

**Roofline 模型**：以算术强度为横轴、可达吞吐为纵轴，画一条"屋顶"线。屋顶的转折点叫 **ridge point**：

- 算术强度低（算得少、搬得多）→ **memory-bound（内存受限）**，紫色区域；
- 算术强度高（算得多）→ **compute-bound（算力受限）**。

**关键结论**：推理的 **decode 阶段是 memory-bound**（要加载全部权重、却一次只预测一个 token，算力浪费、内存成瓶颈）；**prefill 阶段是 compute-bound**（大量 token 并行算，算力拉满）。

### 4. KV Cache（第 2 讲讲过，这里落地）

生成新 token 时，之前 token 的 K、V 已经算过，直接**缓存复用**，不用重算。带缓存的输入比全新输入**便宜约 10 倍**（价格差异）。

### 5. Paged Attention：解决 KV cache 内存碎片化

问题：如果按"最大输出长度"给每个请求预留一整块内存，但实际输出往往远短于上限 → **大量内存被"占着却用不上"（碎片化）**。

解法（Paged Attention）：把内存切成**固定大小 block（B=16 典型）**，用一张**查找表（lookup table）**记录"每个请求的 K/V 存在哪些 block"。碎片化就从"整块内存级"降到"单个 block 级"。

> B 太小 → 查找表元数据爆炸；B 太大 → 又退回碎片化问题。16 是实践中常见值。

### 6. GQA / MLA：减少要存的 K/V 向量

- **GQA（Grouped-Query Attention）**：h 个 query head 共享 g 组 K/V。g=h 就是 MHA，g=1 就是 MQA。例：h=24、g=2 → 省 **91%** 的 KV 内存。实践中 g=2 就很有效（如 Qwen3.8-Flash-Next）。代价是表达力略降（要 grid search 找平衡）。
- **MLA（Multi-Latent Attention）**：用 LoRA 式低秩分解，把"每 token 的 2h（或 2g）个 K/V 向量"压成**一个共享的小 latent 向量**，只存这一个。是 DeepSeek 用来把 KV cache 压缩到极致的关键技术（第 2 讲提过）。

### 7. Speculative Decoding（推测解码）：本讲数学亮点

**动机**：生成慢是因为"逐 token 串行"。但"验证"很快（可以并行）。于是：**用一个小"草稿模型"快速生成 k 个候选 token，再用大"目标模型"并行验证。**

**接受/拒绝规则（rejection sampling）**：

```
对每个候选 token：
  若 目标概率 T(x) ≥ 草稿概率 D(x)  →  接受
  否则                              →  以概率 T(x)/D(x) 接受
                                      否则拒绝，用「残差分布」重新采样
```

**为什么这样能保证输出分布 = 目标模型的分布？**（全概率公式证明，本讲重点）：

用全概率公式拆成"接受"和"拒绝"两支：

```
P(下一个 token = x)
= P(接受)·P(x | 接受) + P(拒绝)·P(x | 拒绝)
= min(D(x), T(x)) + max(0, T(x) − D(x))
= T(x)                       ← 正好等于目标分布！
```

（第二步到第三步：`min(D,T) + max(0, T−D)`，分 T≥D 和 T<D 两种情况，都等于 T。推导里那个"残差分布"= `max(0, T(x)−D(x)) / Σ max(0, T(x')−D(x'))`。）

**两个实用价值**：

1. **下一个 token 免费**：验证时目标模型已经把候选都过了一遍，顺带得到了下一个 token 的概率，不额外花；
2. **拒绝 = 浪费**：一旦拒绝就退出循环，草稿之后的工作白做 → 所以要尽量让草稿和目标"对齐"。

**让草稿对齐的两个办法**：
- **知识蒸馏**：训练小模型去拟合大模型的输出分布；
- **多 token 预测（multi-token prediction）**：同一个 LLM 同时训练 k 个输出头，前 k 个当草稿、第 1 个当验证器（自己当自己的草稿）。

## 关键数字速记

- HBM ~100GB（慢）、SRAM ~100MB（快 10×）；H200 显存 141GB。
- 100B 参数 × FP16(2字节) = 200GB 参数存储（超过单卡）。
- Flash Attention 训练 GFLOPS 75.2 vs 标准 66.6（更高但更快）。
- GQA：h=24、g=2 → KV 内存省 91%；g=1=MQA，g=h=MHA。
- Paged attention 典型 block 大小 B=16。
- 输出价格 ≈ 输入价格的 5 倍。
- 带缓存输入 ≈ 新输入的 1/10 价格。
